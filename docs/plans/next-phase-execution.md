# 下一阶段执行方案：能力契约与阶段验收可信化

> 状态标签：**拟议**（待实施）。主题：把已有的两项真实能力（HTTP 观察、TCP 探测）做扎实，**不**继续堆扫描能力，也**不**宣称通用 Agent 能力。

## 0. 为什么是这个主题

现状盘点（见 `phase-delivery-map.md`）暴露的核心问题不是功能少，而是**可信度缺口**：

1. 能力目录散落多处，"已实现/已配置/可调度/历史验证"混为一谈；
2. 可提前拒绝的输入（缺授权、预算不足、能力不支持）可能触发付费模型调用；
3. 阶段复核不验证证据对象实际存在，缺对象/内容不符仍可能 achieved；
4. 统一工作流在真实提供方下的验收场景不全。

## 1. 工作项与验收标准

### W1 收敛能力契约（服务端统一能力目录）
- 把散落在 `pkg/security/objective.go:126-137`（task/tool 配对）、`pkg/pi/config.go:33-73`（工具注册）、`internal/app/runtime.go:81-90`（Worker 注册）的 capability 定义收敛为单一目录模块。
- 目录条目区分四态：`implemented`（代码存在）/ `configured`（运行时已启用）/ `schedulable`（有可用 Worker）/ `verified`（有验收记录引用）。
- **验收**：Planner、执行校验、Worker 注册、UI 全部从同一目录取定义；未注册或未配置能力无法进入计划或执行；四态在 API 中可见。

### W2 前置失败与错误分类
- 创建阶段统一授权声明校验、最小任务预算（当前前端 `maxTasks=1` vs 后端最少 2 的不一致一并修正）。
- 保留规划失败分类，不折叠成通用失败；明确区分：缺授权 / 预算不足 / 能力不支持 / 范围越界 / 计划不合法。
- 明确文档化：自然语言 objective 中的限制 ≠ 结构化 scope 硬约束。
- **验收**：四类输入分别在**不触发付费模型、不触碰目标网络**的前提下返回明确原因；`needs_work → failed` 路径带结构化缺口信息（对应 `pkg/engine/stages.go:416-430`）。

### W3 证据完整性验收
- stage review 补充证据对象存在性 + 内容 hash 读回校验（当前只查索引，见 `pkg/runtime/review.go:14-40`）；重 IO 放 Run 锁外，提交时重核版本。
- 阶段失败输出结构化缺口列表（缺对象 / 内容不符 / digest 过期 / 缺端口证据 / 缺任务证据）。
- 修正 `self_review` 文案：复核者参与过阶段工作 ≠ 单 Worker 自检。
- **验收**：人为删除一个证据对象后，对应阶段不得 achieved；复核过程零网络探测、零模型费用。

### W4 统一工作流真实验收（隔离环境）
- 隔离数据库 + 本地授权靶场，逐场景验收：单 URL / 裸 IPv4 / 双阶段依赖 / 单 Worker / 多 Worker / 取消 / 缺证据 / 预算耗尽。
- 真实提供方验证单独执行并记录费用许可；离线协议夹具、真实模型、浏览器验收三类证据分开陈述。
- **验收**：每场景记录配置版本、输入、Run ID、实际用量、结果；不宣称泛化成功率。

### W5 文档与交付
- 输出能力矩阵（四态）、阶段状态机差异说明、可复验命令清单。
- 修正 README.md:40 关于 Pi Task 租约恢复的表述（`MaxRetries=0`，过期即 timeout）。
- `web/pi-console-notes.md` 标注为历史资料。
- **验收**：每个"完成"都有代码引用或本阶段实际验收记录；未执行项标 pending。

## 2. 实施顺序与依赖

```
W1 能力目录 ──► W2 前置失败 ──► W3 证据完整性 ──► W4 真实验收 ──► W5 文档
     └──────────────┬──────────────────────────────┘
                    └─ W4 依赖 W1-W3 的验收标准先行冻结
```

- W1 → W2 强依赖（错误分类需要能力目录判定"能力不支持"）。
- W3 可与 W2 并行（不同模块：runtime/review vs engine/planning）。
- W4 必须最后（验收对象是 W1-W3 的产出）。

**环境依赖**：现有 Go/PostgreSQL/Node/Pi 配置、本地授权靶场（`PI_ALLOWED_CIDRS=127.0.0.1/32`）、隔离数据库。不引入新框架、不升级依赖。

## 3. 非目标（本阶段明确不做）

- 不增加任意 Shell / 外部插件 / 范围扩张 / 漏洞利用 / TSecBench 私有协议。
- 自动补充重规划、自动重扫**另立阶段设计**：须先明确用户授权、Run 级预算、修复次数上限、版本与幂等策略；不得直接解除现有 `needs_work → failed` 的拒绝策略。
- 不做生产多租户认证。

## 4. 回滚策略

- 全部改动限制在 Go 服务端与前端展示层；不改 14 张业务表 schema，无迁移回滚负担。
- W1 能力目录先以纯函数模块落地并行的旧路径保留一版：异常时按配置回退旧校验路径。
- W3 的证据读回校验设为可配置开关（默认开），故障时可关闭恢复旧行为。
